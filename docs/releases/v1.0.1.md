# AgriCore v1.0.1 release manifest (prepared)

## Status

This is a pre-publication scope and provenance checklist for the next
maintenance source release. It intentionally records no `v1.0.1` target SHA,
CI run, Docker Publish run, container tag or digest, or GitHub Release URL.
The document does not create an annotated tag, publish a package, or prove a
production deployment.

The [v1.0.0 release manifest](v1.0.0.md) and its published source-release
record remain historical references. They are not evidence for v1.0.1.

## Candidate scope

- Notification validates a source-matched, version-1
  `SensorReadingReceived.v1` payload and commits it as a no-op instead of
  sending valid raw telemetry to the IoT DLT. Wrong source, topic, version, or
  payload schema still fails directly to the DLT.
- Focused regression coverage was added around Identity authentication and
  signing, Inventory stock and harvest boundaries, and Sales saga recovery and
  Inventory-client behavior.
- Release, security, deployment, evidence, and contributor documentation now
  distinguish the prepared v1.0.1 source-release flow from the historical
  v1.0.0 record.

The scope above is not a successful verification result. The final source
target and its evidence are established only by the required workflow.

## Required provenance flow

1. Prepare one exact default-branch revision whose Maven POMs, root and console
   `package.json` files, and Helm chart `version` and `appVersion` all equal
   `1.0.1`. `release-provenance` enforces those equalities.
2. Let the default-branch `ci.yml` push run complete successfully for that
   exact revision. `docker-publish.yml` is eligible only for that successful
   default-branch revision.
3. Docker Publish builds one candidate per application image, scans the exact
   candidate digest, verifies Docker Hub/GHCR parity, signs both registry
   digests, promotes only seven-character and full-SHA tags, then re-verifies
   the promoted references. It never promotes `latest`.
4. Create an **annotated** `v1.0.1` tag at the then-current default-branch tip.
   The `release-provenance` workflow rejects a non-SemVer or lightweight tag, a
   stale target, or a target without matching successful CI and Docker Publish
   runs.
5. The workflow rechecks that the default branch has not advanced, then creates
   the GitHub Release with the exact target and required run links. That GitHub
   Release is the canonical source-release record when present.

## Deliberately absent evidence

| Required record | This prepared manifest |
|---|---|
| Annotated `v1.0.1` source-tag target | Deliberately omitted until workflow validation |
| Exact successful default-branch CI run | Deliberately omitted until workflow validation |
| Exact successful Docker Publish run | Deliberately omitted until workflow validation |
| Full-SHA package tags, signatures, and resolved digests | Deliberately omitted until publication verification |
| GitHub Release URL | Deliberately omitted until `release-provenance` creates it |

## Deployment boundary

A source tag, workflow success, immutable image tag, signature, or digest does
not prove an operator deployment. Locate packages from the verified full-SHA
tag, resolve each to its immutable digest, verify the signature, and use an
environment-owned Helm values file with `repository@sha256:<digest>` image
references. Operators remain responsible for infrastructure, secrets,
ingress/TLS, backups, Kafka authorization, retention, rollout approval, and
runtime evidence.
